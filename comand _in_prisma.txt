2️⃣ Syncing Your Prisma Schema ↔︎ Database
a) Create the first migration (run once after you first write models)
bash
npx prisma migrate dev --name init
What it does

Step	Description
migrate dev	Interactive – creates a migration file under prisma/migrations/, applies it to the dev DB, and runs prisma generate.
--name <label>	Human‑readable identifier (e.g., add_store, add_unique_constraints).
On success you’ll see ✔ Generated Prisma Client.	
Important: prisma migrate dev requires an interactive terminal. In CI/deployments you must use prisma migrate deploy instead (non‑interactive).

b) Apply pending migrations later (e.g., after pulling new code)
bash
npx prisma migrate deploy
Used in production / CI pipelines where you don’t want any prompt.

c) Make quick schema changes without a migration (useful while prototyping)
bash
npx prisma db push   # pushes schema to DB, **does not** create migration files
Only use db push for development iterations or when you deliberately do not want versioned migrations.

d) Introspect an existing database (pull tables into Prisma)
bash
npx prisma db pull
npx prisma generate   # always run after db pull
You already ran this – it rewrote your schema.prisma to match the live Neon DB.

3️⃣ Common Prisma CLI Commands – When to Use Them
Command	When to Run	What It Does
prisma generate	After any schema change or after db pull	Generates/updates the type‑safe client (./generated/prisma).
prisma format	Anytime you edit schema.prisma	Auto‑formats the file (keeps it tidy).
prisma studio	Want a quick UI to explore data	Opens a web UI (http://localhost:5555) to view & edit rows.
prisma migrate status	Inspect migration history & pending steps	Shows applied migrations vs. files on disk.
prisma migrate reset --force	Development only – wipe DB & replay all migrations (what you just did).	Drops everything, recreates schema from migration files.
prisma migrate dev --name <name>	Add/modify models, create a new versioned migration.	Interactive; writes migration folder, updates DB, regenerates client.
4️⃣ Using the Generated Prisma Client in Code
After any prisma generate, you’ll have a ready‑to‑import client.

ts
// src/prismaClient.ts
import { PrismaClient } from '@prisma/client';
export const prisma = new PrismaClient();
Example: CRUD on User & Store
ts
// src/example.ts
import { prisma } from './prismaClient';
// ----- CREATE -----
async function createUserWithStore() {
  const user = await prisma.user.create({
    data: {
      name: 'Alice',
      email: 'alice@example.com',
      stores: {
        create: [
          { storeName: 'Alice Boutique', isActive: true },
          { storeName: 'Alice Marketplace', isActive: false },
        ],
      },
    },
    include: { stores: true }, // return the nested stores
  });
  console.log('Created user with stores:', user);
}
// ----- READ -----
async function listStoresForUser(userId: number) {
  const userWithStores = await prisma.user.findUnique({
    where: { id: userId },
    include: { stores: true },
  });
  console.log('User stores:', userWithStores?.stores);
}
// ----- UPDATE -----
async function activateStore(storeId: number) {
  await prisma.store.update({
    where: { id: storeId },
    data: { isActive: true },
  });
}
// ----- DELETE -----
async function deleteUser(userId: number) {
  await prisma.user.delete({ where: { id: userId } });
}
// Run a demo
async function main() {
  await createUserWithStore();
  await listStoresForUser(1);
}
main()
  .catch(e => console.error(e))
  .finally(() => prisma.$disconnect());
Tip: Because the client is type‑safe, VS Code (or any TS IDE) will autocomplete fields like stores, userId, etc., based on your schema.

6️⃣ Dealing with Unique Constraints & Migration Warnings
When you added storeName and subDomain as String? (optional) but later marked them @unique, Prisma warned:

“A unique constraint covering the columns [storeName] will be added. If there are existing duplicate values, this will fail.”

How to resolve

Check existing rows (via prisma studio or a raw SQL query) to ensure no duplicates.
If duplicates exist, either:
Clean them up manually, or
Add a temporary migration that makes the column nullable and removes the @unique, fix data, then add @unique back.
Running prisma migrate dev interactively will prompt you to confirm the addition of the unique indexes.

8️⃣ Frequently‑Asked‑New‑Developer Questions
Question	Short Answer
Do I need to run prisma generate after every migration?	Yes—migrate dev does it automatically; CI pipelines need to call it manually after migrate deploy.
What’s the difference between db push and migrate dev?	db push updates the DB without a migration file (no version history). migrate dev creates a migration file and updates the DB, giving you a reproducible history.
Can I edit a migration file after it’s been applied?	Only before it’s been applied to any environment. Once applied, create a new migration to change things.
How do I reset the DB without losing data?	Use prisma migrate dev to create a new migration that adds columns/constraints. Only migrate reset drops everything. For production, use data migrations (SQL scripts) instead of resetting.
Where is the generated client located?	In ./generated/prisma (as you configured). Import with import { PrismaClient } from '@prisma/client';.
Do I need a .env file?	Yes—DATABASE_URL="postgresql://USER:PASS@HOST:PORT/DATABASE?schema=public" should be present. Prisma reads it automatically.

How to Push a New Schema Update to Your Database
Below is the exact workflow you should follow in your StoreVerse‑1.0 project whenever you add or change a model/field in prisma/schema.prisma.

1️⃣ Make the change in the Prisma schema
Edit c:\Users\20061\Desktop\StoreVerse-1.0\prisma\schema.prisma (e.g. add a new column, a relation, or a new model).
Tip: run npx prisma format afterwards to keep the file nicely formatted.

bash
# Example – add a “description” field to Store
# (open the file, insert the line, then save)
model Store {
  id              Int      @id @default(autoincrement())
  userId          Int
  image           String?
  storeName       String?
  category        String?
  businessAddress String?
  country         String?
  currency        String?
  subDomain       String?
  isActive        Boolean  @default(true)
  sslEnabled      Boolean  @default(false)
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  description     String?   // <-- NEW FIELD
  user            User     @relation(fields: [userId], references: [id])
}
2️⃣ Generate a versioned migration (recommended for any production code)
bash
# Run from the project root:
npx prisma migrate dev --name add_store_description
What happens
1️⃣ Prisma creates a new folder under prisma/migrations/ (e.g. 20260602120000_add_store_description/).
2️⃣ It applies that migration to your development database (your Neon DB).
3️⃣ It automatically runs prisma generate so the client is up‑to‑date.
Interactive note – migrate dev asks you to confirm any new unique constraints or potentially destructive changes. Answer the prompts (usually just “y”).

3️⃣ If you only want to push the current schema without keeping a migration history (quick prototyping)
bash
npx prisma db push
What it does – Sends the schema directly to the database, creating/altering tables as needed, but it does not write a migration file. Use this only while you are still experimenting; commit a migration later before you ship to production.

4️⃣ Deploying to a non‑interactive environment (CI / production)
Push the already‑committed migrations:

bash
# In your CI script or on the production server
npx prisma migrate deploy   # non‑interactive, runs all pending migrations
npx prisma generate         # re‑generate the client for the new DB shape
migrate deploy is the safe, non‑interactive counterpart to migrate dev. It will fail if a migration would cause data loss unless you explicitly allow it.

5️⃣ Quick command cheat‑sheet (copy‑paste)

New endpoint that receives { email, otp }.

On success it:
Issues a JWT (jwt.sign(...)).

// Verify OTP after login
export const verifyOtp = async (req: Request, res: Response) => {
  const { email, otp } = req.body;
  // …validation logic…
  const token = jwt.sign(
    { userId: user.id, email: user.email },
    process.env.JWT_SECRET!,
    { expiresIn: '7d' }
  );
  await prisma.user.update({
    where: { id: user.id },
    data: { loginOtpCode: null, loginOtpExpiry: null },
  });
  return res.json({ message: 'Login successful', token });
};

How it works (step‑by‑step)
Client → /login (email + password)
Server verifies credentials, generates an OTP, stores it, and returns the OTP (or sends it via email/SMS in production).

Client → /verify-otp (email + OTP)
Server validates the OTP, issues a JWT, clears the OTP, and responds with the token.

Subsequent requests include the JWT in Authorization: Bearer <token> as usual.

Security tip: In production, never return the OTP in the response; instead, send it through a secure channel (email, SMS, authenticator app). Also consider rate‑limiting OTP attempts and using a stronger random generator.
